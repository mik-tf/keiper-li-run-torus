# Lean pilot for T4 (runs at most 593) and T7: trust level for the numerics

Pilot run 2026-11-25, one thread, `nice -n 19`, Lean v4.36.0, Mathlib from the cache only (`lake exe cache get`;
the pilot modules themselves import no Mathlib). Machine: shared 16-core desktop, load 30 to 43 during the runs, so
CPU times (user seconds) are the figure to trust, not wall time.

## The chunk

Adapted from the paper 2 checker (`checkZero`, `keiper-li-sign-runs/lean/KeiperComb/Numerics711Core.lean`),
with the comb exponents replaced by the dense window 0..593:

- Data: zeros 2 to 21 of `code/z2000.json` (0-indexed 1..20; the grid `gamma_mid = N/2^30`, half-width 1025 units of
  2^-30, as in paper 2), against all 48 dense weight vectors of `code/vectors_c2.json` (L = 594, weights over 2^50).
- Per (zero, vector): exact Gaussian-integer Horner evaluation of `B D^593 = sum_j beta_j Zc^j D^(593-j)`
  with `q = Zc/D` the exact unit vector `e^{i theta}` (no trig), then the two integer checks of paper 2
  (witness `rho >= 2^40 |B|`, and the Lipschitz-transfer bound `U`). 960 (zero, vector) checks.
- Files: `P3Lean/Core.lean` (checker), `Weights.lean` and `Data.lean` (generated by `gen_pilot.py`),
  `Kernel.lean` (`decide +kernel`), `Native.lean` (`native_decide`).
- Not written in this pilot: the soundness glue (Lipschitz transfer, the 48-arc cover chain, Lemma wb). The pilot
  measures only the arithmetic, which is where the cost is.

## Times (CPU user seconds, one thread)

| Run | CPU |
|---|---|
| Weights module (48 x 594 numbers, elaboration, one-off, shared by all chunks) | 40 s |
| `native_decide`, 20 zeros x 48 vectors (960 checks), incl. data elaboration | 8.2 s (about 0.38 s per zero) |
| `decide +kernel`, 1 zero x 2 vectors | 13.9 s (about 12.8 s above the import baseline, 6.4 s per zero-vector) |
| `decide +kernel`, 1 zero x 48 vectors | not finished: stopped by the CPU limit at 293 s (consistent with 48 x 6.4 s = 307 s) |

Peak memory about 0.8 GiB (kernel and native), far under paper 2's 10 GiB chunk limit.

## Extrapolation to 2000 zeros x 48 vectors (96,000 checks)

| Route | Total CPU | Notes |
|---|---|---|
| `decide +kernel` | about 170 CPU-hours (6.4 s x 96,000 = 614,000 s) | about 3 times the 30 to 60 hours guessed in the plan; 200 chunks of 10 zeros take about 51 CPU-min each |
| `native_decide` | about 17 CPU-minutes (2000 x 0.38 s = 13 min, plus about 4 min to elaborate the data and 40 s weights) | trust adds the Lean compiler and GMP runtime (`Lean.ofReduceBool` in `#print axioms`) |

The kernel cost is dominated by the dense 594-step Horner (each step a big-integer multiply-add that the kernel
evaluates term by term), not by the integer arithmetic itself. A kernel-friendly rewrite (binary splitting,
fewer unfolded `let`s) might gain 2 to 4 times; that is not measured and not assumed.

T7 (the robust-tail comb, M = 6 troughs, 2000 zeros) was not piloted: it is paper 2's comb checker, whose measured
total for the 622 tier is about 48 CPU-minutes under `decide +kernel`. It stays in the kernel route either way.

## Recommendation

1. T7: kernel `decide`, paper 2's trust level (about an hour of CPU, inferred from paper 2's own measurement).
2. T4 numerics: use `native_decide` for the first release, and say in one sentence in the paper that the
   48 x 2000 arc check is done by compiled code, so the trust adds the Lean compiler and runtime. Cost: minutes.
3. Kernel `decide` for T4 only as an optional later upgrade, not a blocker: about 170 CPU-hours.

## Does the full run need the build server?

- `native_decide` route: no. About 17 CPU-minutes fits the desktop.
- Kernel route for T4: yes, 170 CPU-hours (about 11 hours wall on 16 threads, 3 to 4 days on 2 threads).

Steps for the kernel route (not run). As the user `the build user` on the build server:

    curl -sSf https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
    . "$HOME/.elan/env"
    elan toolchain install leanprover/lean4:v4.36.0
    git clone --branch lean https://github.com/mik-tf/keiper-li-run-torus.git "$HOME/keiper-li-run-torus"
    cd "$HOME/keiper-li-run-torus/lean"
    lake exe cache get          # Mathlib cache only, never build Mathlib from source
    LEAN_NUM_THREADS=1 nice -n 19 lake build P3Lean.Weights

Then run the chunk modules, one thread each, in parallel with `xargs -P`, never more than the cores minus 2.

## Reproduce

    cd lean && python3 -I gen_pilot.py 1 21 P3Lean/Data.lean 48     # the committed chunk
    lake build P3Lean.Native                                          # seconds
    python3 -I gen_pilot.py 1 2 P3Lean/Data.lean 2 && lake build P3Lean.Kernel   # kernel timing, 14 s
    # lake build P3Lean.Kernel on the committed chunk takes about 100 CPU-minutes
